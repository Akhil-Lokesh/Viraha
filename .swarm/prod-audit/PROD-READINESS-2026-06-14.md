## Dimension verdicts

### [NOT_READY] backend-correctness-merge
The just-merged likes/SSE feature introduces a BLOCKER-level graceful-shutdown gap and four HIGH-severity correctness bugs that must be fixed before production launch. The two parallel SSE stacks (realtime.ts and sseRegistry.ts) are architecturally redundant and their interaction is unsafe: sseRegistry.ts has no shutdown hook, no per-user connection cap, no sseLimiter coverage, and — critically — createActivity awaits a non-idempotent DB write after the like transaction has already committed, meaning a DB hiccup on the activity row returns 500 to the client while silently leaving the like recorded. The existing error-handling and transaction infrastructure is otherwise solid.

- **BLOCKER BE-1 — sseRegistry has no shutdown function — /notifications/stream connections block graceful shutdown**  
  `/Users/akhil/Desktop/Viraha/backend/src/lib/sseRegistry.ts:1-51`  
  sseRegistry.ts exports only register, unregister, push, listenerCount, _resetRegistry — no drain/shutdown. server.ts calls shutdownRealtime() (realtime.ts) but never drains sseRegistry. Any open /notifications/stream connection prevents server.close() from resolving, hitting the 10-second failsafe and forcing process.exit(1) on every deploy.  
  → Add a shutdownSseRegistry() export to sseRegistry.ts that iterates all listeners, calls res.end() and res.socket?.destroy() on each (mirroring realtime.ts shutdownRealtime), then clears the registry. Import and call it in server.ts gracefulShutdown alongside shutdownRealtime().
- **HIGH BE-2 — createActivity DB failure returns 500 after the like transaction has already committed**  
  `/Users/akhil/Desktop/Viraha/backend/src/controllers/reactionController.ts:67-89`  
  Lines 67-74: prisma.$transaction([reaction.create, post.update(increment)]) commits. Line 76: await createActivity(...) is called — if prisma.activity.create inside createActivity throws (e.g. FK violation, connection drop), the exception propagates into the outer catch at line 87 and next(err) fires a 500. The like IS saved and likeCount IS incremented; the client has no way to know. The same applies to the comment, save, and follow activity paths.  
  → Wrap the await createActivity(...) call in its own try/catch inside reactionController (and any other controller that calls it after a state-changing transaction). Log the failure at warn level and continue to send the success response. Alternatively, make createActivity itself fully absorb all errors — currently only publishActivity is guarded, not the prisma.activity.create call.
- **HIGH BE-3 — sseRegistry has no per-user connection cap — a single user can exhaust server file descriptors**  
  `/Users/akhil/Desktop/Viraha/backend/src/lib/sseRegistry.ts:7-21`  
  register() unconditionally adds to the Set with no upper bound. realtime.ts enforces MAX_CONNECTIONS_PER_USER = 5 and closes the oldest connection when exceeded. sseRegistry.ts has no equivalent. A client that reconnects rapidly (or a tab-duplication bug) accumulates unlimited /notifications/stream connections per user in the same process.  
  → Add a MAX_CONNECTIONS_PER_USER constant (match realtime.ts value of 5) to sseRegistry.ts. In register(), while set.size >= MAX_CONNECTIONS_PER_USER, pop the oldest res from the Set, call res.end(), and delete it before adding the new one.
- **HIGH BE-4 — likeCount has no database-level floor constraint — decrement can write negative values**  
  `/Users/akhil/Desktop/Viraha/backend/prisma/migrations/20260517053500_add_reactions/migration.sql:2`  
  Migration adds like_count INTEGER NOT NULL DEFAULT 0 with no CHECK (like_count >= 0). Math.max(0, updated.likeCount) in reactionController line 62 only clamps the API response value — it does not prevent the negative write from being stored. Data corruption at pre-existing likeCount=0 plus a concurrent or replayed unlike request would persist -1 in the DB.  
  → Add a migration: ALTER TABLE posts ADD CONSTRAINT posts_like_count_floor CHECK (like_count >= 0). Also consider using a PostgreSQL advisory lock or a conditional UPDATE (WHERE like_count > 0) for the decrement instead of an unconditional decrement.

### [NOT_READY] performance-scalability
The application has two parallel SSE subsystems where only one (realtime.ts via /activities/stream) uses Redis pub/sub for multi-instance delivery; the other (sseRegistry.ts via /notifications/stream) is pure in-memory and will silently drop notifications for any user connected to a different backend process, making horizontal scaling impossible for that path. The cache invalidation layer uses Redis KEYS (O(N) blocking scan) in production-latency paths, which will freeze the entire Redis keyspace under load. The feed hot path lacks a composite index covering the leading isDeleted predicate alongside postedAt, forcing a full scan on large tables before the index kicks in. The Prisma client is instantiated without any connection pool configuration, leaving it at the default 10-connection cap regardless of database server capacity. Map page marker thumbnails and PhotoTile (used everywhere cards appear) use raw img tags, bypassing Next.js image optimization and serving uncompressed full-resolution images on every render.

- **BLOCKER PERF-1 — In-memory sseRegistry breaks horizontal scaling — notifications lost across processes**  
  `/Users/akhil/Desktop/Viraha/backend/src/lib/sseRegistry.ts:5`  
  const registry = new Map<string, Set<Listener>>(); — a pure in-process Map. activity.ts line 44 calls sseRegistry.push() after publishActivity(), which already delivers through Redis pub/sub on the realtime.ts path. So /notifications/stream (notificationStreamController.ts line 18) has NO cross-process delivery; any user whose SSE connection lands on a different backend pod will never receive a notification. The two SSE streams (/activities/stream → realtime.ts with Redis pub/sub; /notifications/stream → sseRegistry.ts with no pub/sub) are architecturally inconsistent.  
  → Remove the sseRegistry push in activity.ts (line 44-51) entirely — realtime.ts already delivers the same payload via Redis pub/sub to all processes. The /notifications/stream route should either be removed (it is redundant with /activities/stream) or migrated to use realtime.ts's publishActivity/sseHandler pair. Once sseRegistry is no longer called for cross-user delivery, the BLOCKER is closed.
- **HIGH PERF-2 — Redis KEYS used in cache invalidation — O(N) blocking scan that stalls Redis under load**  
  `/Users/akhil/Desktop/Viraha/backend/src/lib/cache.ts:46`  
  cacheDelPattern calls redis.keys(pattern) (line 46), which is a synchronous full-keyspace scan in Redis. cache-invalidation.ts calls cacheDelPattern('feed:*'), cacheDelPattern('map:*'), cacheDelPattern('explore:*') on every post create/update/delete. KEYS blocks all other Redis commands while it runs; on a keyspace of tens of thousands of entries this can stall the 25-second SSE heartbeat timers, rate-limiter lookups, and session reads for hundreds of milliseconds.  
  → Replace redis.keys(pattern) + redis.del(...keys) with a SCAN-based iteration loop (ioredis pipeline + SCAN 0 MATCH pattern COUNT 100) or, preferably, use structured key namespaces with a Redis Set that tracks active keys per namespace so invalidation is O(members) without a keyspace scan.
- **HIGH PERF-3 — Post feed/search/map queries missing composite index on (isDeleted, postedAt) — full index scan on hot paths**  
  `/Users/akhil/Desktop/Viraha/backend/prisma/schema.prisma:102-109`  
  Feed query (feedController.ts line 48) is: WHERE isDeleted=false AND userId IN (...) ORDER BY postedAt DESC. The only indexes on Post are @@index([userId]), @@index([postedAt]), @@index([privacy]), @@index([userId, privacy, postedAt]), and @@index([saveCount]). None include isDeleted as a leading column. PostgreSQL cannot use [userId, privacy, postedAt] when the WHERE clause has userId IN (list) AND isDeleted=false because isDeleted is absent — the planner may resort to the single-column [postedAt] or [userId] index and then filter isDeleted in-flight across all rows. The same gap affects postController.getPosts (line 58) and searchPosts (line 289).  
  → Add @@index([isDeleted, postedAt]) and @@index([isDeleted, userId, postedAt]) to the Post model in schema.prisma, then generate and run a migration. The feed query planner will then use the composite index to skip deleted rows before evaluating the userId IN filter.
- **HIGH PERF-4 — Prisma client has no connection pool configuration — defaults to 10 connections regardless of database capacity**  
  `/Users/akhil/Desktop/Viraha/backend/src/lib/prisma.ts:5`  
  new PrismaClient() with no datasources or log options. Prisma's default connection pool is min=0, max=10 (for Node.js). A production backend under moderate load (e.g., 50 concurrent requests each doing 3-4 queries) will queue at the pool, adding 50-200ms of pool-wait latency to every request. There is also no DATABASE_URL ?connection_limit= or ?pool_timeout= parameter set.  
  → Instantiate PrismaClient with an explicit pool size matched to the server's CPU count and database server limits, e.g., new PrismaClient({ datasources: { db: { url: env.DATABASE_URL } } }) and append ?connection_limit=25&pool_timeout=10 to DATABASE_URL, or set the PRISMA_CONNECTION_LIMIT env var. For multi-instance deployments behind a PgBouncer, set ?pgbouncer=true.

### [NOT_READY] infra-deploy-observability
Two blockers prevent safe production launch. First, the application runs two independent in-process SSE registries — the notifications path (`sseRegistry.ts`) is never drained during graceful shutdown, leaving open sockets that prevent `server.close()` from completing cleanly under Railway's 10-second failsafe. Second, the frontend Sentry configs call `Sentry.init()` unconditionally without checking for a DSN, which causes Sentry to emit a console error on every page load in environments where `NEXT_PUBLIC_SENTRY_DSN` is unset, and the variable itself is absent from both env example files. Beyond the blockers, several high-severity gaps exist: `NEXT_PUBLIC_SITE_URL` is a build-time required arg used by sitemap and OG metadata but is undocumented in both env examples; `pino-pretty` is in production `dependencies` rather than `devDependencies`, adding unnecessary weight to the production image; and the CSP `script-src` directive contains `'unsafe-inline'` in the frontend, which substantially weakens XSS protection. The remaining items (no Node version pin, no `engines` field, single /health endpoint serving both Railway liveness and readiness) are low-to-medium risk and are workable at launch.

- **BLOCKER INFRA-1 — Dual SSE registries — sseRegistry.ts is never drained on graceful shutdown**  
  `backend/src/server.ts:35`

### [READY_WITH_RISKS] data-model-migrations
The core schema is structurally sound: the Reaction model is correctly defined with a composite unique index on (userId, postId, type), FKs with CASCADE on both sides, and like_count is maintained inside a $transaction that atomically pairs the reaction row with the counter update, making concurrent double-like/double-unlike safe. However, a migration (20260320160521_phase3_emotional_core) silently reverted every TIMESTAMPTZ column back to TIMESTAMP(3), meaning the entire app stores timestamps without timezone awareness. Three additional lower-severity issues exist: like_count has no DB-level CHECK constraint so it can go negative on unusual concurrent delete paths; the PlaceNote NULL-placeId partial index is not representable in schema.prisma so a prisma migrate reset would lose it; and Activity.actorId has no standalone index making user-deletion cascade and any actor-based query a full scan.
